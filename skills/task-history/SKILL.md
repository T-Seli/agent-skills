# Central task history

The private `agent-task-history` repository holds the cross-session record. This central writer is separate from `agent_skills/history.py`, which remains a compact local timeline; do not write the same event through both without an explicit reference. The project `TASK/log.md` remains the local receipt and retains its existing parsed tokens and record commits. Never copy a raw project log wholesale into central history.

## New task and handoff workflow

When central history is configured (contracts.md § Task log; decided by `history.py configured`: exit 0 prints the checkout, else `History: not configured`), the designated record owner creates one stable task ID at the first substantive work checkpoint. Inspect the checkout and `INDEX.md` first so a resumed task does not get a second journal. Append a `start` event with exact scope, excluded scope, approval reference, execution owner, known repository and code identity, and open checks. At material decisions, failed approaches, code/test/review/deploy checkpoints, and final handoff, append one sanitized event for the meaningful change. This is an explicit producer step, not a background session capture. Workers and subagents deliver evidence packets to the record owner; they do not independently append to the same task.

For each checkpoint, fetch and reconcile the private checkout, append the event with the expected digest through `checkpoint_capture.py`, render and write `views/<task-id>.md`, and add or update the `INDEX.md` row linking the view and `events/<task-id>.jsonl`. Keep any older `tasks/<task-id>.md` as a labeled historical snapshot. Publish the journal, view, and index together, then run `checkpoint_capture.verify_publication` against a fresh reader checkout to verify their event ID, digest, generated marker and index links. A consumer resuming the work reads the index and full journal, checks the current repository state, and consumes the current revision/digest in its task readback while distinguishing what it independently verified from what an earlier owner reported. A same-owner fresh-clone readback proves retrieval only; it is not an owner transfer, independent verification, or native-runtime capture proof. If the history checkout, permission, source pin, owner or publication path is unavailable, retain the pending stage, leave a sanitized packet or task-local receipt and report the publication gap at handoff; do not claim central capture succeeded or block unrelated authorized work.

Use `history.py --repo <isolated-history-checkout> view <task-id> --events` before resuming. For a readable narrative, run `markdown.py --repo <checkout> <task-id>` to print a deterministic Markdown overview and chronological implementation log. `markdown.py --repo <checkout> <task-id> --write` maintains only `views/<task-id>.md`; it refuses to overwrite user edits. Existing `tasks/*.md` and project logs are never rewritten. Summarize its newest event and unresolved checks, then verify referenced Git state and current environment independently. Treat history as a lead, not as approval or proof that a reported action happened.

At start, material decisions, failed attempts, code/test/review/deploy milestones, and handoff, write a small JSON evidence packet using the fields in `schema.json`. Run `view` to obtain the current digest, then `append <packet> --expected-digest <digest>`. For a new task use the SHA-256 digest of empty bytes and a `start` event with `revision: 1`, `schema_version: 1`, and `status: active`. Each later event increments revision by one. After a fresh clone run `history.py --repo <checkout> init` to set private permissions on only the event directory and files. Reuse the same `event_id` on uncertain retries; an identical retry is a no-op. If a digest or lock conflict occurs, stop writing, read the newest record, reconcile IDs and ownership, then retry with the newly observed digest. Never overwrite unseen history, delete a lock without investigating, force-push, or infer a successful write from an interrupted command.

One record owner writes each task. Workers and subagents send sanitized evidence packets to that owner. An owner change requires a `handoff` event by the current owner with `new_record_owner` and `transfer_ack_ref`; the new owner writes from the next revision. A stale owner is rejected. Record the execution owner separately. Scope and approval references must identify the exact authorized action; neither a worker report nor a prior log implies a new approval. For commands, tests and deployment claims, include full SHA, environment, outcome and restricted evidence reference. Any independently verified evidence, including on test, review or deploy events, carries `verified_revision`. A `verification` or `close` event also carries `verified_revision` equal to the prior current revision and independent passing evidence bound to that revision’s recorded `head_sha`, environment, and execution owner. Unknown code identity cannot be verified. A failed or unknown independent verification remains a valid historical event. A close requires a prior wholly passing verification, no unresolved checks, passing close evidence, and an exact approval reference; it cannot resolve checks itself. Historical corrections do not change current status. Include `source_version` and `runtime_version` when available; missing version facts remain explicit uncertainty. Label each claim `performed`, `reported`, or `independently_verified`; only independent verification names its verifier. Mark stale SHA claims and missing evidence as uncertainty; never silently upgrade them.

Keep `summary` short for the current overview; record `context`, `implementation`, `module_changes` (path, what, why), `decision`, `reason`, `failed_approach`, `validation`, `outcomes`, `monitoring`, limits and next step when evidence supports them. A coordination milestone uses the existing event schema and summarizes only a contract revision/readback, decision, material blocker, release gate or acceptance result; start from `examples/coordination-milestone.json` and retain its precise sanitized evidence references. Use `repo_ref` and `branch_ref` with SHA/environment to disambiguate code evidence. The Markdown view shows current state separately from latest activity and never invents prose or turns a reported test into independent verification. An omitted `next_step` inherits the prior actionable step, a new `next_step` supersedes it, and `clear_next_step: true` explicitly removes it; terminal states clear it permanently. Each event keeps its historical instruction in the chronological log. Lessons are `proposal` events for later human review, with observed evidence and potential counterexamples. No skill or instruction text changes automatically from these proposals.

For orchestration friction, use a `feedback` event owned by the existing task record owner. Start from the [small example packet](examples/feedback-event.json), replacing its synthetic IDs and claims. It requires a sanitized `source_ref` and labeled evidence plus `feedback_category`, `feedback_issue`, `feedback_impact`, `feedback_correction`, `feedback_prevention_check`, and `feedback_check_state`. Record `unverified` until the prevention check is run. A passing or failing check needs `feedback_check_ref` and performed evidence with that exact reference and a matching pass or fail outcome; a reported claim is insufficient. This check state describes whether the prevention check ran and passed; it is not an independent verification claim. If a cause is included, pair `feedback_cause` with `feedback_cause_basis: observed` or `hypothesis`. An observed cause needs performed or independently verified evidence; a canceled tool call or user correction alone does not establish it. A later feedback event can report the check outcome, referencing the earlier event with `correction_of` when correcting its claim. Feedback does not change lifecycle status, resolve an open check, approve an action, or modify future skills. Send a separate reviewed `proposal` if a general workflow change is warranted.

Record encountered system/tool failures even when recovery succeeds: the observed failure and effect, exact sanitized source/version/environment, attempted correction and actually verified recovery path. Use existing failure/feedback fields and evidence references; do not infer a cause from acknowledgment, cancellation or a prepared fix. Keep prevention `unverified` until its own check has run with matching evidence, even if immediate recovery passed. An owner acknowledgment or locally prepared packet is not durable capture; report the exact append/render/index/publish/readback stage and unresolved recording gap. Inspect the existing journal before retrying an uncertain write, preserving the event ID.

Sanitize before writing. Do not include private assistant notes, raw chats, full transcripts, secrets, customer payloads, personal data or broad session-directory captures. Link restricted artifacts by precise reference without copying their contents. `history.py` has a conservative reject filter, not a complete privacy scanner: the writer reviews each packet. The tool only edits a local checkout. Fetch, compare and reconcile remote history before any eventual publication; publication follows the repo's review and approval process.

Only start, decision, failure, cancellation, and close can change status; terminal states cannot reopen through a historical event. Use `status` only for state changes; a late proposal or historical receipt cannot reopen a canceled task or restore its actionable next step. Track unresolved items through `open_checks` and `resolved_checks`. Only a wholly passing independent verification or a scoped decision with approval reference and reason can resolve checks. A close cannot add or resolve checks. Use `at_utc` for when an action occurred and `observed_at_utc` for when this owner saw its evidence. Include base/head SHA and a dirty-diff digest when code state matters; an old SHA is historical evidence, never a claim about the current checkout. Corrections append a new event with `correction_of`, preserving the original. Reading and replaying events only rebuilds a summary; it never executes recorded commands.

The CLI requires the checkout root to have `origin` set to `T-Seli/agent-task-history` on GitHub. The central event store and compact local `agent_skills.history` are distinct during the pilot; link receipts explicitly. If replay reports a corrupt or incomplete tail, retain the valid prefix and inspect/reconcile the raw file before any repair. The task-history skill is in `agent_skills/catalog.json`; changes to its source still require adapter-specific validation and installation. A source or catalog change does not activate new runtime behavior.
