# Current behavior and completion

Read with contracts.md for every task; retain behavior details in the existing plan/task record, without another tracker.

## Depth, not breadth

Improve rigor within the authorized task, not its size. Before substantive work, identify the professional quality bar for this exact outcome; the rawest authorized primary evidence; the methods and tools suited to that evidence; and an independent observable check that could falsify the result. Use these to execute the task, without replacing execution with prompt rewriting or an unsolicited interview. A summary is a lead: trace material claims to primary sources when available. If evidence or tools are unavailable, name the gap, qualify the claim and continue independent authorized work; never probe denied access or widen permissions.

Choose methods proportionate to risk: for investigations, reconstruct the timeline and test competing explanations; for engineering, trace producers/consumers and reproduce the defect; for analysis, inspect source data and assumptions. Verify against source artifacts, regression behavior, measurements or another independent standard, rather than your own assertion or the user's agreement. State what would disprove the conclusion and what remains unverified. More agents, tools, tests, deliverables or scope are not inherently deeper. Preserve privacy, exclusions, settled decisions and all permission gates; seek a new decision only for a material action outside existing authority.

Rewrite a prompt only when asked. For that request, answer the four checks first, then rewrite for exactly that deeper task, retaining scope and gates. Preserve this original prompt as the reference:

> I want a deeper version of this task, not a bigger one. Before rewriting it: (1) say what a top professional in this field would do here that I’m not asking for; (2) name the rawest material they would start from instead of what has already been digested for me; (3) name the specific methods and tools they would use; (4) say what, other than you or me, would show the result is right. Then rewrite my prompt to ask for exactly that.

## One current contract

Reconcile the latest authenticated user instruction for this task with its owner and approved scope before proposing, dispatching or asking again. A newer decision supersedes a conflicting old summary only within its actual scope; preserve exclusions, deferrals and independent approvals. A thread or overview is a view, not authority. When they disagree, inspect the original decision and current source, then update the existing pointer: owner, artifact/revision, next action and decision reference. A failed card write leaves that view unsynchronized; say so without undoing canonical progress or claiming the update landed.

## Behavior matrix

Maintain one current approved matrix in the plan or task artifact. Check source before calling a capability missing; reuse or correct an existing capability before proposing a duplicate. Trace every affected producer and consumer, including alternate entrypoints. Record unchanged paths explicitly when they matter.

| Case / concrete input | Current capability and source | Approved behavior / exceptions | Prompt, KB or backend delta and producer paths | Risk / observable check | Decision reference / held or deferred work |
| --- | --- | --- | --- | --- | --- |

Bind the matrix to its exact artifact revision/digest, repository commit or dirty-source digest, and environment. Carry that identity through blueprint, action-items and handoff. A proposed row remains proposed until its own approval is authenticated; do not import approval from another row or task. Show added customer-flow steps and who must perform them. An apparently small prompt edit can add a material new step or reach another producer path.

A decision brief states the issue, a concrete example, the actual prompt/KB/backend change (or unchanged component), regression risk, and the exact decision/action/target being requested. Cite the matrix/source identity; usable facts stay inline. Do not ask an already resolved decision again.

## Independent completion conditions

Use existing gates and obligations to track implementation, deployment, observed behavior acceptance and promised manual/customer follow-through separately, when relevant. Each unmet condition has an owner, next action, source and receipt needed to close it. A deployed or verified code artifact cannot close an unsent promised reply. Preserve reply holds and deferred work through the next day and handoff; technical work can finish while the overall request remains open. Sending still needs the task's existing communication authority.

An admitted task or prepared packet has not executed. Confirm the assigned executor and actual execution receipt; reconcile an uncertain start before dispatching again. Approval does not imply admission, execution, verification or customer outcome. A healthy deployment with no observed relevant behavior leaves behavior acceptance unverified. Existing manual waivers remove only their named check, not the need for positive outcome evidence.

## Proportionate proof and portable handoff

For small instruction changes, check semantic outcomes on bounded synthetic examples and affected paths. Reuse exact referenced evidence only when its relevant source, tests, dependencies and environment are unchanged; state that comparison. Do not demand identical generated prose or repeat paid/live simulations merely because a review or handoff is fresh. Material risk or changed paths need new relevant proof; consent, exact-source integrity and rollback still apply.

The next owner must be able to read the cited artifact. Check the destination's supported access or inline the essential matrix rows, decisions and open conditions within the handoff's 40-line/450-word cap, explicitly marking inaccessible detail. A local path alone does not prove remote access. Keep one current pointer; label older artifacts historical. Installing source on one Mac does not update separate personal adapters, saved environments or loaded sessions. Return their exact source-pin/change package to the supported owner rather than inventing an installation route.
