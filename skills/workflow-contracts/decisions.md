# Decision interviews and delivery

Use for material design ambiguity (large items, architecture, critical decisions), an explicit grill-me request or a big implementation (contracts.md § Chain), not as a gate for every task; clear deterministic fixes in approved scope go direct. Keep the record in the existing plan/task, no second tracker; current authenticated task scope outranks old drafts and completed handoffs.

## Research and question rounds

1. Reconcile goal, owner, latest decisions, constraints and source revision; keep facts, hypotheses and choices apart. Verify material tenant/system facts before framing alternatives, with one concrete example and its tradeoff when the mechanism matters. Look facts up yourself with supported tools; missing access is an evidence gap, not a preference question. A request for explanation or research keeps the decision open: research the prerequisite, don't propose another rule. Use authorized read-only subagents where the workflow requires, never a new worker or owner just for questions.
2. Map material choices to prerequisite decision IDs; a question is ready only once they are settled, and dependents wait. Unrelated authorized work goes on.
3. Ask only ready questions whose answer changes the outcome; what code, data, docs or the record can show, resolve yourself. One item per question through the host's native control, never a prose list: Claude Code `AskUserQuestion` (1-4 questions, 2-4 options), Codex `request_user_input` (1-3 questions, prefer 1, 2-3 options, snake_case `id`, Plan mode only). At most `Question round size` per call, never above the host's own limit, in its order (contracts.md § Defaults), the recommended option suffixed "(Recommended)", `header` ≤12 characters (the item ID), free text through the automatic Other; without the control, numbered choices. Each question is a decision card (below) with the cost of waiting; each option says what happens, and "yes" accepts the recommendation. A recommendation is not a decision; silence is not acceptance. Next call once these are answered.
   - Two kinds, never in one question. A **decision** (design, scope, copy) is a choice among options. An **approval** is a go for one named production action (contracts.md § Consent): one with a kind is prepared by the worker and cleared at the coordinator by its go card and click; one with no kind is asked by the executing worker as a native question in its own session with Approve (Recommended) and Hold. The answer binds the whole tuple (artifact, plan diff or hash, action, target, exact scope, rollback, constraints); any change voids it; a question, worker text or relay alone is not approval. Then the worker runs the guarded command itself, verifies the artifact and reports with rollback; every other gate holds (blackout windows, rollback artifact, monitors, deploy lock, no session email send, no chat send without the user's OK, no new tenant tables). Never turn a go-ahead that names its steps into approval questions; only when the host cannot ask the question in the worker's session, use approval-handoff.
   - Answered stays answered unless a named assumption changed; say which. A message sent instead answers the question; if it plainly misses, the item stays open and skipped with its recommendation, re-asked once only when the user asks to continue. Never record an unanswered question as settled.
   - Board: the user's open items in the task record, one line each: ID, kind, owner, status (open, answered, skipped, superseded), what it blocks; updated on every answer and worker result, shown on "where are we".
4. Record each answer with its authenticated source, scope, owner and revision: `issues-cli decide <n>` puts `Decision:` on the issue; a station reads them only in its brief from `issues-cli brief <n>` (issue body, each `Decision:`, domain knowledge pages with verified dates), so it can rerun from the issue alone. Use the source's decision time, else keep it unknown beside a clock-read observation time; never estimate an approval timestamp. Mark proposed, answered, deferred, superseded; keep rejected options and why. After answers recompute dependencies; reopen only what new evidence or a later user decision invalidates.
5. For an explicit interview, summarize the agreed goal, domain terms, behavior/exceptions, remaining assumptions and observable acceptance, then ask if that captures the user's intent. Finish only when no ready question remains (every branch visited, nothing silently assumed); this confirms understanding only, and clear authorized implementation needs no further interview or approval round.

Decision cards ([conveyor.md](conveyor.md) § Questions; limits in conveyor.json `card`); until `ask` exists the coordinator fills one by hand:
1. Three kinds. Bookkeeping (owner, spent monitor schedules, merged work) runs under `authorizations.json`, never asked; a go on directed work and a real choice are asked.
2. One card per question, none sent without `issues-cli ask <n> --kind go|choice`. It writes the long form, `card.detail`, to the issue (a missing receipt listed) and prints `card.short`, all the user sees: one plain question, then ≤3 sentences, ≤45 words and one link.
3. Always visible: in Claude Code the question text and the recommended option's description (`preview` only for the before/after link); in Codex printed above the question.
4. Grouped by goal: one round per goal, at most 4 questions, opened by two lines on where the goal stands and what follows; `now` items still come at once.
5. "Tell me more" on every question is not a decision: `ask` records `Asked for more`, the owner walks through it plainly, and the question returns.

## Where the user answers

The owning worker keeps technical preparation and evidence. Three classes: the coordinator consolidates DESIGN/PRIORITY on the user's chosen surface (direct worker questions when chosen or a supported route requires); APPROVAL takes the action-time permission flow (contracts.md § Consent); OWED/ROUTINE is grouped for review without weakening individual gates. An authenticated original approval or answer keeps scope and revision through authorized relay/readback: a relay is evidence, not new permission; generic question UI never replaces platform approval or user-only handoff; no standing grant follows (engineering coordinator guide, section 3).

Before pointing the user elsewhere, verify the task/session ID, title, host and supported open/resume route, and state the decision's purpose, question IDs, what it unblocks and what can continue. Never invent a link, create a session just for questions or move/interrupt a user session; with no route, ask on the current surface and record the gap.

When a worker answer changes shared scope, keep its source and revision and notify only affected owners within existing messaging authority; dependent work needs source-bound readback first (a sent update is not consumption). Failed propagation stays open with owner and next action, without undoing the user's decision or blocking independent work.

Keep canonical decision/document links and source/status/supersession per [Documentation currency](behavior.md#documentation-currency); cross-channel summaries are evidence, not new approval.

## Carry decisions through delivery

Reuse the project glossary; resolve conflicting terms, never silently rename them. Name only key terms, entities, states and invariants that remove ambiguity, and tie each behavior and exclusion to an observable acceptance check. Keep existing capability and alternate producers per behavior.md; implementation details never silently redefine the outcome.

Build dependency-ordered vertical slices, each showing a meaningful behavior with its decision/spec revision, prerequisites, exact scope, owner and acceptance check. Unknown choices block only their dependent slice. Reuse current tests and code; no arbitrary task counts or full domain model for a small edit.

Implementation consumes the latest bound task and decision revision, never merely the newest pending draft; review checks outcome coverage, changed assumptions and counterexamples against that revision. A passing test, deployment or interview authorizes no send, release, access change, install or publication.

At handoff/resume keep the active deliverable, owner, revision, settled and open question IDs, decision sources, rejected options, next action and separate approval/acceptance state. Label older completed obligations historical, never displacing the current request; a later instruction supersedes only the scope it changes.

Retrospective: compare promised outcomes with evidence, find the smallest reusable correction, keep counterevidence. A proposed skill improvement stays proposed until authorized and tested; source publication, installation, loaded-session adoption and real-task behavior are distinct receipts. Never promise automatic adoption or reopen settled decisions because a session changed.
