# Decision interviews and delivery

Use for material design ambiguity, an explicit grill-me request or a big implementation (contracts.md § Chain), not as a mandatory gate for every task. Keep the record in the existing plan/task; no second tracker. Current authenticated task scope takes precedence over old drafts and completed handoffs. Use this for large items, architecture and critical decisions when material choices remain unresolved. Proceed directly with clear deterministic fixes within existing approved scope.

## Research and question rounds

1. Reconcile the goal, existing owner, latest decisions, constraints and source revision. State facts, hypotheses and choices separately. Verify material tenant/system facts before framing alternatives; use one concrete example and its tradeoff when the mechanism affects the choice. Look up available facts yourself with supported tools; missing access is an evidence gap, not a preference question. A request for explanation or more research keeps the decision open; research the prerequisite instead of proposing another rule immediately. Use authorized read-only subagents when the calling workflow requires them; do not create another worker session or owner merely for questions.
2. Map material choices to prerequisite decision IDs. A question is ready only when its prerequisites are settled; dependent questions wait. Continue unrelated authorized work while evidence or answers are pending.
3. Ask only ready questions whose answer changes the outcome. Research first: whatever code, data, docs or the task record can show is yours to resolve, not a question. One item per question through the host's native control, never a prose list: Claude Code `AskUserQuestion` (1-4 questions, 2-4 options), Codex `request_user_input` (1-3 questions, prefer 1, 2-3 options, snake_case `id`, Plan mode only). Common shape: at most 3 per call (contracts.md § Defaults `Question round size`), recommended option first and suffixed "(Recommended)", `header` of at most 12 characters (the item ID), free text through the automatic Other. Without the control, use the same shape as numbered choices. Each question stands alone, because the user may see only the dialog: what is asked, the one fact that matters, and what waiting costs, in about 250 characters; each option says what happens. Word it so "yes" accepts the recommendation. A recommendation is not a decision; silence is not acceptance.
   - Two kinds, never in one question. A **decision** (design, scope, copy) is a choice among options. An **approval** is a go for one named production action: action, target, scope, with Approve (Recommended) and Hold. Never turn a go-ahead that already names its steps into approval questions (contracts.md § Consent). Carry a verified original approval as source-bound relay evidence (contracts.md § Consent); only when the host requires the approval in the worker's own session, give the user one paste-ready `Approved:` line and the verified session to paste it in (approval-handoff).
   - Order: prerequisite first, then time-critical and unblocking items; put the cost of waiting in the question. Send the next call when these are answered.
   - Answered stays answered unless a named assumption changed; say which. A question the user closed by sending a message is answered by that message: apply it. If the message plainly does not address the item, keep it open and skipped on the board with its recommendation, and re-ask it once only when the user asks to continue the items. Never record an unanswered question as settled.
   - Board: keep the user's open items current in the existing task record, one line per item: ID, kind, owner, status (open, answered, skipped, superseded), what it blocks. Update it on every answer and worker result, and show it on "where are we".
4. Record each answer with its authenticated source, scope, owner and revision in the existing task record. Use source-recorded decision time when available; otherwise keep it unknown and record a clock-read observation time separately. Never turn estimated chronology into an approval timestamp. Distinguish proposed, answered, deferred and superseded. Retain rejected options and why. Recompute dependencies after answers; reopen only affected choices when new evidence or a later user decision invalidates them.
5. For an explicit interview, summarize the agreed goal, domain terms, behavior/exceptions, remaining assumptions and observable acceptance, then ask whether that captures the user's intent. Finish only when no ready question remains: every branch visited, nothing silently assumed. This confirms understanding only. Already clear, authorized implementation need not undergo another interview or approval round.

## Where the user answers

The owning worker retains technical preparation and evidence; the coordinator consolidates ready user-facing design/priority questions on the user's chosen surface. Direct worker questioning remains available when explicitly chosen or required by a supported route, not as a mandatory context switch. Preserve authenticated original answers, scope and revision through authorized relay/readback; a relay is evidence, not new permission.

Route three classes: DESIGN/PRIORITY consolidated by the coordinator from worker evidence; APPROVAL through the actual supported action-time permission flow when required; OWED/ROUTINE grouped for review without weakening individual gates. Prefer supported native structured questions with a recommended option first; otherwise equivalent numbered choices. An authenticated original approval may travel by the existing supported evidence relay per Consent; generic question UI never substitutes for platform approval or user-only handoff. No new standing grant follows. See the engineering coordinator guide, section 3.

Before pointing the user elsewhere, verify the actual task/session ID, title, host and supported open/resume route. State the one decision's purpose, its question IDs, what it unblocks and what work can continue. Do not invent a link, create another session just for questions or move/interrupt a user session. If the route is unavailable, present the question on the current surface and record the gap.

After a worker answer changes shared scope, preserve its source and revision; notify only affected owners under existing communication authority. Require source-bound readback before dependent work relies on the change. A sent update is not consumption. Keep failed propagation open with its owner and next action, without undoing the user's valid decision or blocking independent work.

Keep canonical decision/document links and source/status/supersession per [Documentation currency](behavior.md#documentation-currency); cross-channel summaries are evidence, not new approval.

## Carry decisions through delivery

Reuse an existing project glossary when available; resolve materially conflicting terms rather than silently renaming them. Use consistent domain names in the existing plan: key terms, entities, states and invariants only when they remove ambiguity. Tie each desired behavior and exclusion to an observable acceptance check. Preserve existing capability and alternate producers per behavior.md; implementation details do not silently redefine the requested outcome.

Build dependency-ordered vertical slices that each demonstrate a meaningful behavior. Every item carries its decision/spec revision, prerequisites, exact scope, owner and acceptance check. Unknown choices block only their dependent slice. Reuse current tests and code; do not mandate arbitrary task counts or a full domain model for a small edit.

Implementation consumes the latest bound task and decision revision, never merely the newest pending draft. Review checks outcome coverage, changed assumptions and counterexamples against that same revision. A successful test, deployment or interview does not authorize a send, release, access change, install or publication.

At handoff/resume preserve the active deliverable, owner, revision, settled and open question IDs, decision sources, rejected options, next action and separate approval/acceptance state. Explicitly label older completed obligations historical so they cannot displace the current request. A later instruction supersedes only the scope it actually changes.

Retrospective: compare promised outcomes with evidence, identify the smallest reusable correction, and retain counterevidence. A proposed skill improvement stays proposed until authorized and tested; source publication, installation, loaded-session adoption and real-task behavior are distinct receipts. Never promise automatic adoption or reopen all settled decisions because a session changed.
