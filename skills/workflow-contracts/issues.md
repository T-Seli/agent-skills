# Issues: tracked tasks

The one home for issue tracking. Skills cite it; they never restate it. Implement publishes every task that lands a code change in a repo the project CLAUDE.md § Map `Issues` names (`<owner/repo>`, more than one allowed). Any task whose `plan.md` records `Issue: <owner/repo>#<n>` (written by the helper, or from an issue input) is tracked, and the steps below apply to it. Neither: no issue steps, said once in the report. It needs the `gh` CLI signed in. Every call below goes through the release-bound helper, spelled exactly `~/.agents/skills/workflow-contracts/scripts/issues-cli` and unquoted (`ICLI` below), so one permission rule can allow it; `--dry-run` prints each write instead of making it.

## Which work
- Anything that lands a code change gets one issue when its plan or one-line plan is approved. A question, investigation or blueprint Answer that changes no code gets none by default; explicitly admitted decisions, investigations, monitoring and human follow-through may use existing issues in the user's shared queue. Do not publish every conversation.
- Branch flow normally lands an implementation-scoped task through one PR whose `Closes` lines close its issues. Stronger issue acceptance gates take precedence: use nonclosing references until they are met. Trunk flow has no PR: nothing closes them automatically, so `/deploy` closes eligible issues after its record (**Close**). If accepted issue scope includes a separate deployment, use `Refs <owner/repo>#<n>` until its deployment gate is verified; retain actual observation/human obligations beyond the deploy record too. Do not expand implementation-only scope into a deployment requirement or create a new issue merely to hide an unmet gate.
- A big implementation (contracts.md § Chain) gets a spec issue plus one sub-issue per ticket, with blocked-by links for each `after #k`.
- A task that starts from an issue (`#<n>` or its URL as the input) uses that issue as its spec: blueprint reads it, and the plan's header records `Issue: <owner/repo>#<n>` so nothing new is created for it.

## Format
- Spec issue: the plan in the reader's words, under `## Problem Statement`, `## Solution`, `## User Stories` (big implementations), `## Acceptance criteria` and `## Out of scope`; label `ready-for-agent` when the repo has it. A single-task issue uses `## What to build` and `## Acceptance criteria`. No file paths, internal tool names or customer data in titles or bodies.
- Ticket sub-issue: the session writes `issue-text.md` in the draft, one `## <n>. <title>` section per ticket with a plain what-to-build paragraph and `- [ ]` criteria a person can check, never copied from the worker ticket. The helper adds `## Parent` and `## Blocked by` (from `action-items.md`) and refuses a ticket without its section.

## Shared queue and local working copy
- When the user designates GitHub as the shared queue, issues hold the current human-readable goal, accountable owner, priority, next action, blockers and evidence links. `plan.md` and `action-items.md` remain the detailed execution working copy. Use [github-queue.md](references/github-queue.md) at admission, resume, material changes and handoff; never preload the whole queue into each worker.
- The helper writes `Issue: <owner/repo>#<n>` under the plan's title and `· issue #<n>` on each ticket line, so a rerun creates nothing. Reuse the existing issue before creating a duplicate.
- Reconcile later human edits and current native issue/PR facts before dispatch. Changed scope reaches the running plan through **Iterate** in blueprint, not silent worker drift. Hold affected slices while the owner resolves conflicts; continue independent authorized work. A comment or label never grants implementation, release or messaging authority.

## Who and when
- Only the session running the task acts on issues: the orchestration session for a big implementation, else the session running `/implement`. Ticket workers, the merger and the fixer never touch issues; their brief carries `Issue: #<n>`.
- **Publish** at implement's Start record: write the spec or task body to a scratch file, then (tickets: after writing `issue-text.md`) `ICLI publish --repo <owner/repo> DRAFT --title "<title>" --body-file <file> [--label ready-for-agent]`. Tickets publish in the same call.
- **Claim** right after: `ICLI claim --repo <owner/repo> <n> --branch <type>/<slug>`; use `--session` when the host does not supply a verified ID. It assigns the signed-in user and leaves one comment naming the branch and session. It refuses an issue assigned to someone else (ask the user; never take it over) and one filed by someone else unless the user OK'd claiming it (`--approved`). Preserve the accountable human owner separately from the executing session; do not run claim when its assignment would replace that owner. It also refuses when another session holds the latest claim note (ask the user, then `--takeover`); deduplication includes the exact session, so a successor updates its pointer only with that OK and without changing the human owner. Claiming is a best-effort guard, not a lock: the first claim note after the read wins, a loser posts a `Released:` note, and the owner is the latest claim not released, and only the login that wrote a claim can release it.
- **Draft PR** (branch flow) at the first authorized push: title = the plan's title; body = the plan's one-line goal and explicit issue links. `ICLI closes DRAFT` emits `Closes <owner/repo>#<spec>` plus one repository-qualified reference per ticket (using the plan's single repository, even in another repository's PR; missing/invalid/ambiguous metadata refuses): inspect each against its closure gate, using nonclosing references for unmet deployment, observation or human obligations. One task, one PR; a big implementation opens it from its integration branch. Verify actual closing relationships and target branch, not keywords alone.
- **Tick** only proved criteria: `ICLI tick --repo <owner/repo> <ticket n> --evidence-file <receipt.json>`. The [evidence schema](references/issue-evidence.md) binds the current body and exact criterion text/number; only supplied verified criteria change. Legacy calls without evidence refuse. Retain open deployment/acceptance checks.
- **Ready** (branch flow) at an authorized readiness review's test-review YES: `gh pr ready <PR>`, except a release-member PR (behavior.md § Release train), which stays draft until merged into the release branch; only the release PR is marked ready. Advisory draft review retains draft status and never triggers this step.
- **Close** only at the issue's stated acceptance gate. Branch flow: after the project's authorized release route, check actual merged/closed metadata; report discrepancies rather than forcing closure. Native closed/merged is not deployment or functional acceptance. Preserve unmet obligations on the current issue or an explicitly agreed linked follow-through issue; never silently weaken its gate. Trunk flow: only after verified deployment and every issue's closure criteria, `ICLI close --repo <owner/repo> DRAFT --sha <full sha> --evidence-file <receipt.json>` preflights the complete open set, requires exact-body evidence for every checked criterion plus deployment/closure receipts, and closes eligible tickets then the spec. Missing/stale proof refuses before any closure. Receipts are supplied assertions, not independent backend verification; GitHub writes are not an atomic batch. Reconcile any partial network outcome instead of blindly retrying.

## Consent
- The first live issue in a repo needs the user's explicit go-ahead, recorded as `Approved:` per contracts.md § Consent.
- After that, approving a plan or ticket breakdown covers publishing its issues, and claiming, commenting, ticking, the draft PR and closing the task's own issues after its deploy record are routine.
- Always ask first: claiming an issue someone else holds or filed, editing any issue the task did not create, and publishing in a repo neither § Map `Issues` nor the user names.
- Explicit task restrictions override routine authority above. Preparing a queue reconciliation or review does not authorize posting it, issue edits/closure, workflow activation, credentials, security settings or deployment. Missing write authority blocks publication only, not read-only reconciliation or independent authorized implementation.
