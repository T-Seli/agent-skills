# Issues: tracked tasks

The one home for issue tracking; skills cite it, never restate it. Implement publishes every task that lands a code change in a repo § Map `Issues` names (`<owner/repo>`, one or more). A task whose `plan.md` records `Issue: <owner/repo>#<n>` (by the helper or from an issue input) is tracked. Neither: no issue steps, said once in the report. It needs `gh` signed in. Every call goes through the release-bound helper, spelled exactly `~/.agents/skills/workflow-contracts/scripts/issues-cli` and unquoted (`ICLI` below), so one permission rule can allow it; `--dry-run` prints writes instead of making them.

## Which work
- Anything that lands a code change gets one issue when its plan or one-line plan is approved. A question, investigation or blueprint Answer that changes no code gets none by default; explicitly admitted decisions, investigations, monitoring and human follow-through may use existing issues in the user's shared queue.
- Branch flow normally closes an implementation-scoped task's issues by its one PR's `Closes` lines; a stronger acceptance gate wins, with nonclosing references until met. If accepted issue scope includes a separate deployment, use `Refs <owner/repo>#<n>` until its deployment gate is verified, and keep actual observation/human obligations past the deploy record. Never expand implementation-only scope into a deployment requirement or open an issue to hide an unmet gate. Only where accepted scope requires a deployment that the merge is not does the release owner close it after the deploy record; implementation-only issues keep `Closes`.
- A big implementation (contracts.md § Chain) gets a spec issue plus one sub-issue per ticket, with blocked-by links for each `after #k`.
- A task started from an issue (`#<n>` or its URL as input) uses it as its spec: blueprint reads it and the plan's header records `Issue: <owner/repo>#<n>`, so nothing new is created.

## Format
- Spec issue: the plan in the reader's words, under `## Problem Statement`, `## Solution`, `## User Stories` (big implementations), `## Acceptance criteria` and `## Out of scope`; label `ready-for-agent` when the repo has it. A single-task issue uses `## What to build` and `## Acceptance criteria`. No file paths, internal tool names or customer data in titles or bodies.
- Ticket sub-issue: the session writes `issue-text.md` in the draft, one `## <n>. <title>` section per ticket with a plain what-to-build paragraph and `- [ ]` criteria a person can check, never copied from the worker ticket. The helper adds `## Parent` and `## Blocked by` (from `action-items.md`) and refuses a ticket without its section.

## Shared queue and local working copy
- With GitHub as the user's shared queue, issues hold the human-readable goal, accountable owner, priority, next action, blockers and evidence links; `plan.md` and `action-items.md` stay the detailed working copy. Use [github-queue.md](references/github-queue.md) at admission, resume, material changes and handoff, never preloading the whole queue into a worker.
- The helper writes `Issue: <owner/repo>#<n>` under the plan's title and `· issue #<n>` on each ticket line, so a rerun creates nothing; reuse an existing issue rather than duplicate it.
- Reconcile later human edits and current issue/PR facts before dispatch. Changed scope reaches the running plan by **Iterate** in blueprint, not worker drift; hold affected slices until the owner resolves conflicts; independent work continues. A comment or label never grants implementation, release or messaging authority.

## Who and when
- Only the session running the task acts on issues (a big implementation's orchestration session, else the one running `/implement`). Ticket workers, the merger and the fixer never touch issues; their brief carries `Issue: #<n>`.
- **Belt** ([conveyor.md](conveyor.md)): an open belt issue has one `lane:<name>` label. Only the guarded `ICLI lane <n> <lane>` moves it, refusing with each missing entry receipt named; a move back needs `--reason`. `publish` sets lane `next` and posts the `Owner:` line (accountable login, session, time); a claim never replaces it.
- **Publish** at implement's Start record: write the spec or task body to a scratch file, then (tickets: after `issue-text.md`) `ICLI publish --repo <owner/repo> DRAFT --title "<title>" --body-file <file> [--label ready-for-agent]`. Tickets publish in the same call.
- **Claim** right after: `ICLI claim --repo <owner/repo> <n> --branch <type>/<slug>`, `--session` if the host gives no verified ID. It assigns the signed-in user and comments once with branch and session. It refuses an issue assigned to someone else (ask the user; never take it over) and one filed by someone else unless the user OK'd it (`--approved`). Never run it where its assignment would replace the accountable human owner. It also refuses when another session holds the latest claim note (ask the user, then `--takeover`); deduplication includes the exact session, so a successor updates its pointer only with that OK. A claim is a best-effort guard, not a lock: the first note after the read wins, a loser posts `Released:`, the owner is the latest unreleased claim, and only its writing login can release a claim.
- **Draft PR** (branch flow) at the first authorized push: title = the plan's title; body = its one-line goal and explicit issue links. `ICLI closes DRAFT` emits `Closes <owner/repo>#<spec>` plus one repository-qualified reference per ticket (the plan's single repository, even in another repository's PR; missing/invalid/ambiguous metadata refuses): check each against its closure gate, with nonclosing references for unmet deployment, observation or human obligations. One task, one PR; a big implementation opens it from its integration branch. Verify actual closing relationships and target branch, not keywords.
- **Tick** only proved criteria: `ICLI tick --repo <owner/repo> <ticket n> --evidence-file <receipt.json>`. The [evidence schema](references/issue-evidence.md) binds the current body and exact criterion text/number; only supplied verified criteria change, and calls without evidence refuse. Keep open deployment/acceptance checks.
- **Ready** (branch flow) at an authorized readiness review's test-review YES: `gh pr ready <PR>`, except a release-member PR (behavior.md § Release train), which stays draft until merged into the release branch; only the release PR is marked ready. Advisory draft review keeps draft status.
- **Close** only at the issue's stated acceptance gate. Branch flow: after the authorized release route, check actual merged/closed metadata and report discrepancies rather than force closure; native closed/merged is not deployment or functional acceptance. Unmet obligations stay on it or an agreed linked follow-through issue; never silently weaken its gate. Trunk flow (no PR; `/deploy` after its record): only after verified deployment and every issue's closure criteria, `ICLI close --repo <owner/repo> DRAFT --sha <full sha> --evidence-file <receipt.json>` preflights the open set, requires exact-body evidence for each checked criterion plus deployment/closure receipts, and closes eligible tickets then the spec; missing/stale proof refuses before any closure. Receipts are supplied assertions, not backend verification; GitHub writes are no atomic batch, so reconcile a partial outcome, never blindly retry.

## Consent
- The first live issue in a repo needs the user's explicit go-ahead, recorded as `Approved:` per contracts.md § Consent.
- After that, an approved plan or ticket breakdown covers publishing its issues; claiming, commenting, ticking, the draft PR and closing the task's own issues after its deploy record are routine.
- Always ask first: claiming an issue someone else holds or filed, editing any issue the task did not create, and publishing in a repo neither § Map `Issues` nor the user names.
- Explicit task restrictions override routine authority. Preparing a queue reconciliation or review authorizes no posting, issue edit/closure, workflow activation, credentials, security settings or deployment. Missing write authority blocks only publication, not read-only reconciliation or independent authorized work.
