# Iterative user-path critique

UI design is not one-shot. Plan at least two critique rounds against the same
selected direction: first candidate interaction/critique, then focused improvement
and fresh verification. If the first pass finds no justified change, the second
round still challenges different tasks/states; do not manufacture cosmetic churn.

## Planning and handoff
The design/spec/short-plan output names the loop, even before anyone may run it:
“After selection and scoped execution authority, two independent UI-capable
perspectives interact and capture screenshots; critique → fix → another round →
exact-final retest. Resolve stable findings against task success within budget,
or report open gaps, responsible owner and next scoped action.” Adapt the wording, retain these decisions.
Do not run workers or browser actions without their scoped authorization; read-only planning may use authorized scouts/architects within blueprint's limits. Planning never authorizes live-state changes or proves checks passed.
Two rounds are a minimum feedback cycle, not proof of convergence or a reason to
stop improving while authorized scope and budget remain. Do not add rounds just
to fill a count; budget exhaustion remains an explicit hold, never acceptance.

## Capable independent perspectives

The coordinator owns the loop; one execution owner edits. Use at least two
independent perspectives, such as task usability/visual hierarchy and keyboard/
responsive accessibility. Assign capable subagents with actual local browser,
rendering and screenshot tools; reuse available authorized workers rather than
create tool-limited profiles. Discover capabilities before dispatch. Give the
agreed design packet, local route/fixture, exact revision, user tasks, constraints
and evidence requirements, including explicit allowed scratch/artifact roots per
[execution proof](../../workflow-contracts/references/execution-proof.md), without prescribing conclusions or sharing the other critic's answer first. Never let competing browser controllers operate the same
surface concurrently: use separate isolated views or sequence their interactions.
Resource limits still apply; parallelize safe independent work, not shared edits.

Each critic actually attempts representative user tasks in the local UI, captures
screenshots of relevant states and records actions, observed outcomes and issues
against agreed principles. Read-only/local fixture work only unless a separate
scope authorizes writes: no live submissions, real payments, messages or data
changes. Reviewers do not edit. Screenshot inspection proves only appearance;
action traces plus actual tool receipts support interaction claims. A planned,
simulated or unavailable interaction must be labeled as such, never passed.

## Assignment and finding return

> Evaluate <selected direction/spec revision> at <local route, fixture and source>.
> Perspective: <user task/visual hierarchy or accessibility/responsive>.
> Attempt <tasks/states> using available local UI tools within <scope/budget>.
> Capture screenshots and action/result receipts; report tool/capability gaps.
> Return findings with stable ID, severity/task impact, source/viewport/state,
> evidence, reproduction, principle violated, recommendation and closure check.
> Do not edit, broaden scope or act on live services; stop at unsafe effects.

Keep one findings table in the existing task packet: ID, critic, artifact/round,
actual evidence mode (interactive, screenshot-only, simulated or unavailable),
impact, disposition, fix owner, fix revision, retest receipt and unresolved gap.
The primary reconciles conflicts against user tasks/research, not majority taste.
A delivered critique is not an accepted finding; an accepted fix is not verified.
Preserve dissent/counterevidence and retain the stable ID across rounds.

## Improve, retest and stop

The execution owner fixes accepted in-scope findings; a selected direction does
not authorize redesign or feature expansion. Material choices return to the user
with options/recommendation; hold only dependent edits. Re-render the new exact
candidate and have the relevant critic reattempt the original path and inspect
new screenshots; check adjacent regression states. A matching retest, not a
comment saying fixed or an older screenshot, resolves a finding. Later edits
invalidate affected evidence; verify the final combined candidate.

Declare task-success criteria and reserve independent exact-final retests in the
aggregate budget before starting; if they cannot fit, propose smaller scope or hold.
A practical default is two rounds, with at most one additional round for unresolved
in-scope findings. Stop converged only after multiple independent perspectives,
the second round, and exact-final-artifact verification show task success and no
unresolved blocking findings; record why lower-priority suggestions were deferred.
At budget exhaustion, repeated failure or missing tools, return the best candidate,
open findings, actual coverage and a concrete next action instead of an endless
loop or a false acceptance. User-requested further rounds need their scope/budget.
If browser/render/screenshot/subagent support is missing, continue authorized
wireframe/code or screenshot-only critique and report the interactive loop blocked
with the next supported owner/route. Do not claim a simulated critique was real
user interaction. Actual accessibility/usability review with humans and release
approval remain separate; these instructions do not prove runtime compliance.
